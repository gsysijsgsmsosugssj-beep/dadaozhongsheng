# 通知权限点了"阻止"还能救回来：4 步恢复路径 + 3 个当场验证动作（Chrome/Edge/Firefox/Safari 实测差异）

上周替同事盯一个客服号，网页版第一次加载时右上角弹了条"tlgrkg-web.com 想发送通知"，我正一边回话一边划鼠标，手一抖落在"阻止"上。弹窗消失得比眨眼还快，地址栏左侧却多出一个灰色铃铛，上面压着一道斜杠。当时没当回事，晚上对账才发现那个会话一整晚的消息我一条都没看见——页面开着，角标在涨，通知栏干干净净。

## 一、灰铃铛不是"这次没同意"，是询问权被收走了

很多人以为点"阻止"只是拒绝了这一次弹窗，下次进站它还会再问一遍。不是。浏览器把这件事记成了**持久状态**：这个源（origin）的通知权限从"询问"（default）变成了"拒绝"（denied），并且页面从此**失去了再次弹框的资格**。

这就是为什么你在站点里把"开启通知"开关来回拨十次，屏幕都没反应——它背后的 `Notification.requestPermission()` 一被调用就直接返回 `denied`，浏览器连问都不问你。唯一的出路是你亲手去浏览器那一侧把这条记录改回来。站上关于权限归属的说明在 👉 [网页版通知设置说明](https://tlgrkg-web.com) 里也有对应段落，对着看一眼不会走偏。

顺带说清一个常见误判：有些页面里点"开启通知"毫无反馈、按钮也不变成"已开启"，八成不是站点坏了，而是它已经处在 denied 状态，只能由用户从浏览器设置里解封。判断成本很低——下一节的三个验证动作，第一个就能定性。

## 二、四步恢复：把灰铃铛变回正常铃铛

这四步在四大浏览器上的动作顺序一样，入口名字不同，跟着地址栏找就行。

1. **从地址栏进站点权限面板**。点地址栏最左侧那个图标（Chrome 和 Edge 中文叫"查看网站信息"，老版本叫"网站设置"），展开后找"权限"分组里的"通知"，把下拉从"阻止"改成"允许"。
2. **面板里找不到"通知"这一项时，走设置页的例外列表**。这说明该站点还没成功请求过权限，或者被更高一层的规则接管了。Chrome 打开 `chrome://settings/content/notifications`，页面上半部是"允许"列表、下半部是"不允许发送通知"列表，在被禁站点右侧点三个点选"删除"；Edge 是 `edge://settings/content/notifications`，结构一样。
3. **刷新页面**。站点权限是页面加载时读进内存的，在面板里改完不刷新，脚本里那个 `permission` 值还是旧的，你会以为白改了。
4. **回站点把开关重新打开一次**。有些站点自己存了一份"用户拒绝过"的标记，浏览器放行了它还不敢发，得让它再请求一次。

| 浏览器 | 地址栏入口 | 设置页路径 | 被拒后的显示 |
| --- | --- | --- | --- |
| Chrome | "查看网站信息" → 权限 → 通知 | `chrome://settings/content/notifications` | 地址栏灰铃铛带斜杠 |
| Edge | 锁形图标 → 权限 → 通知 | `edge://settings/content/notifications` | 同上，另有拦截计数提示 |
| Firefox | 盾牌/站点信息 → 权限 → 发送通知 | `about:preferences#privacy` → 权限 → 通知 → 设置… | 面板里状态显示"已阻止" |
| Safari | 不提供地址栏权限面板 | Safari → 设置 → 网站 → 通知 | 该站点右侧下拉显示"拒绝" |

表格里 Safari 那一行是最容易卡住的：它压根没有地址栏权限面板，只能在 `Safari → 设置 → 网站 → 通知` 的列表里，找到站点把右侧下拉从"拒绝"改成"允许"；列表里没有这个站点，说明记录已被清掉，重新访问一次就会重新问。Firefox 的例外列表里选中站点后要点"移除网站"，直接关掉窗口是不保存的。各家入口的文字差异，站上 [各家浏览器的权限入口](https://tlgrkg-web.com) 也分开列了，找不到按钮时按名字搜。

## 三、三个验证动作，少一个都可能只是"假恢复"

权限栏变绿不等于通知能到。按这三步验，任何一步掉链子都指向不同楼层。

1. **看 `Notification.permission` 的实际值**。在网页版页面按 F12 打开控制台，敲 `Notification.permission`，回车。返回 `granted` 才算真放行，返回 `denied` 说明面板里那一改没生效（八成正走在没刷新的旧页面里），返回 `default` 说明记录被删干净了但还没人再请求过。
2. **手动触发一次请求和一次发送**。控制台里依次敲 `Notification.requestPermission().then(console.log)` 和 `new Notification("权限测试", {body:"看到这行字说明链路通了"})`。前者当场弹框，后者立刻出横幅——这一步的好处是不依赖站点自己的逻辑，能把"站点没写对"和"权限没给"分开。
3. **走一遍端到端**。手机端给自己的另一个会话发一条，掐表。五秒内出横幅、点横幅能直接跳到对应会话，算完全通过；只躺进通知中心不出横幅，问题已经不在权限层了，去系统通知样式里看。

| 验证结果 | 说明什么 | 下一步 |
| --- | --- | --- |
| `permission` 仍是 `denied` | 记录没改掉或页面没刷新 | 回第二步，改完强制刷新 |
| 控制台能弹横幅，站点收不到消息 | 站点侧开关没重开 | 回站点设置里重开一次 |
| 有横幅但点不动 | 缺"打开链接"类权限 | 检查弹窗拦截与系统通知交互设置 |
| 全绿但没声音 | 落到免打扰或系统样式 | 与权限无关，另查 |

## 四、改完还是灰的：四种不在权限面板里的原因

- **页面不是 HTTPS**。控制台敲 `window.isSecureContext`，返回 `false` 就说明这个页面根本没有申请通知的资格，权限面板里那一栏改了也不生效。这种情况换到正常入口即可，别在面板里反复折腾。
- **企业策略锁死**。Chrome 地址栏输入 `chrome://policy`，如果看到通知相关的禁止策略，权限面板的下拉会是灰的、点不动——这不是你的操作问题，得找管机器的人。
- **扩展在替你管事**。隐私防护、权限管理类扩展会重写站点权限，甚至把站点依赖的长连接当追踪脚本拦掉。开一个无痕窗口访问同一地址，无痕里能正常弹框，就锁定是扩展的锅。
- **系统层把浏览器整体关掉了**。macOS 进"系统设置 → 通知"找到浏览器、Windows 进"设置 → 系统 → 通知"找到对应条目，开关关着的时候，站点权限写"允许"也一条横幅都不会有。这一层在权限面板里完全看不出来，最容易被漏掉。

还有一种小概率：页面被嵌在别人站点的 iframe 里打开，跨源 iframe 的通知权限一律按拒绝处理，此时无论怎么改外层站点都没用，直接在独立标签页里打开就好。

## 五、把四步压成一张便签

误点"阻止"这件事，麻烦的从来不是点错那一下，而是它留下的状态不吵不闹：没有报错、没有红字，只有一个不显眼的灰色图标，和一段安静得反常的时间。恢复动作其实只有一条主线——**从地址栏权限面板把"阻止"改成"允许"，找不到就删设置页例外列表，改完刷新，回站点重开开关**，然后用 `Notification.permission` 和一条手动 Notification 当场结案。

我现在换设备的第一件事，是先在控制台敲一遍那句 `Notification.permission`，看到 `granted` 再去干别的；同事机器上则固定备一张便签，写着四个浏览器的入口名字。整套动作三分钟内能走完，比事后翻聊天记录找漏掉的消息便宜太多。剩下的界面细节，从 👉 [tlgrkg-web.com](https://tlgrkg-web.com) 的通知章节顺一遍，手就不会再抖到"阻止"上了。
